With batch 6, the owner's approved language list is complete. The seventh batch added the four English regional variants the owner confirmed on Nov 12, 2026: **English — United Kingdom (en-GB), English — Canada (en-CA), English — Australia (en-AU), English — India (en-IN)** — 2,961 keys each (the four batch-7 Settings label keys grew the key count from 2,957), every one wired into the registry, the server allowlist and the Settings select, with per-locale coverage + switch tests. The variants are regional adaptations of the English base, not translations: most values are identical to US English, and only strings that genuinely differ are changed — colour, centre and cancelled in all four; catalogue, fulfilment, uncategorised, organised/authorised and practise (the verb) in the British-spelling regions (en-GB, en-AU, en-IN); cord → cable in the printer help for en-GB and en-AU; and each region's address placeholder names its own fields (postcode for the UK, province + postal code for Canada, state + postcode for Australia, state + PIN code for India). ## Steps

1. Copy `en.js` to `<code>.js` (BCP 47 code, e.g. `es.js`, `fr.js`) and translate every value. Keep the keys exactly as they are — a key is never renamed in a translation file.
2. Keep `{name}` placeholders intact (`scan.onlyOnHand` uses `{count}` and `{location}`) — they are filled in by `t()`. **Exception:** the English plural-agreement markers (`{s}`, `{plural}`, `{suffix}`, `{us}`, `{cs}`, `{ps}`, `{fs}`, `{rs}`) are OMITTED in languages whose plural does not work that way (Arabic omits them — the plural lives in the word form, and keeping one renders a stray Latin letter).
3. Import it in `src/lib/i18n.js` and add it to `LOCALES`:
   ```js
   import { es } from './locales/es.js';
   export const LOCALES = { en, es };
   ```
4. Add the code to the server allowlist in `server/authRoutes.js` (`SUPPORTED_LANGUAGES`) so Settings can save it.
5. Add the option to the Language select in `src/components/business/DetailsCard.jsx` (with a `settings.details.<language>` label key in `en.js` — the language's own name, e.g. `العربية (Arabic)`).
6. Add a test in `src/lib/i18n.test.js`: every `en` key exists in the new locale, every value is a non-empty string, value placeholders match (minus agreement markers), and `t()` with that locale returns the translated string for at least the nav + scan surfaces. See the Arabic test for the pattern.
7. **No surface conversion is needed anymore** — every page, component, and shared lib file already goes through `t()` (T6.3). A new language is a new file in this folder, not a hunt through the pages.

## The public picker + policy translations (Picker build, Nov 12)

- Visitors switch language **before** signing up: `src/components/LanguagePicker.jsx` sits on the landing page, Plans, Subscribe, the three policy pages, and the auth pages (via `AuthLayout`). The choice applies immediately (`setLocale` in `src/lib/i18n.js`, RTL flip included), persists in localStorage under `stockhaven.locale`, is restored at startup by `initLocale()` in `src/main.jsx`, and a business created afterwards starts in that language (client sends it in `createBusiness`; the server validates it against `SUPPORTED_LANGUAGES` and fails soft to English).
- Picker labels come from `LOCALE_LABEL_KEYS` in `src/lib/i18n.js` — the same `settings.details.<language>` keys the Settings select uses.
- The legal pages render per-locale bodies through the registry in `src/lib/policyTranslations.js`: English modules stay the base and the official text; a later pass registers a translated body per locale (`registerPolicyTranslation(kind, locale, body)`), and until then the English body shows. When a translated body shows, the page prints `policies.translationNotice` above it — **every new locale file must include that key** (the English text: the translation is for reading; if there is ever a disagreement, the English version is the official one).

## Translation-debt tranches

Later features (workforce, inbox/messaging, training, the recovery kit, Send-PO, trial reminders, the delete warning, Rewards, POS and its plan gate) landed with their strings propagated as verbatim-English interim into every locale — translation debt. **Tranche 1 (Nov 13, 2026)** retired the debt for the first four locales in ABC order — **Amharic (am), Arabic (ar), Bengali (bn), Bhojpuri (bho)**: every debt key translated, and all three policy bodies translated and registered in `src/lib/policyTranslations.js` (files under `src/lib/policies/`). The debt census definition (byte-identical values minus the legitimately-identical categories: token-only proper/technical strings, example-data placeholders, language labels, the confirmation-word key) lives in `tests/t20/tranche1.test.js`, which pins zero debt for the completed locales. **Tranche 2 (Nov 13, 2026)** retired the debt for the six Spanish variants — **es-MX, es-ES, es-US, es-CU, es-PR, es-VE** — UI keys and all three policy bodies each; the census gained one documented category, the *verified cognate* (a short value spelled identically in correct Spanish — Total, Subtotal, Digital, Roles, Kit, kg, No, "{count} roles" — pinned as exact keys per locale in the t20 test, never a pattern). **Tranche 3 (Nov 13, 2026)** retired the debt for **French (fr-FR, fr-CA)** and **Portuguese (pt-BR, pt-PT)** the same way, each with its own pinned cognate set (French shares many identically-spelled words with English — Description, Dimensions, Total, Notes; Portuguese adds Status, Item, Scanner, Backup). Remaining locales carry roughly 850 debt keys each and retire in later tranches.

## What `t()` does when something is missing

- Unknown locale code → English (never a blank screen).
- Missing key in the active locale → the English string.
- Missing key in English too → the key itself, so the gap is visible.

## Standing rules (learned in batch 3)

- **The Delete Account confirmation word is per-locale: `settings.deleteConfirmWord`.** Every language confirms account deletion with its OWN word — English `DELETE`, Spanish `ELIMINAR`, French `SUPPRIMER`, German `LÖSCHEN`, Arabic `حذف`, and so on (owner's decision, Nov 12, 2026: "everything should translate per language, every single thing"). `src/pages/Settings.jsx` interpolates that word into `settings.delete.enterDelete` and `settings.delete.dialogDescription` via the `{word}` placeholder and matches the typed text against it (trimmed, case-insensitive in the locale's own case rules) through `matchesDeleteConfirm` in `src/lib/i18n.js`. Never hard-code the literal `'DELETE'` as the comparison outside the English strings, and never put a translated word into the prompt strings directly — keep the `{word}` placeholder so the word lives in exactly one place per file.
- **Language label values are identical in every locale file.** `settings.details.<language>` is the language's own name plus its English name in parentheses (e.g. `Français (French)`); never translate the English gloss, and keep `settings.details.english` as `English` in every locale. The merge script inserts these from `labels.json`, and the per-language slice check catches a translated gloss only if you look — check them by hand before merging.

## Translations are Muse-generated, not professionally translated

A native speaker spotting something off later gets it fixed — say so honestly when reporting a new language, and record any judgment calls in the phase report.
